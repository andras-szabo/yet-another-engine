So, let's think about the asset database, loading assets and stuff.

What's the problem we're trying to solve?
   We'd like to be able to access some kind of asset using an asset type and a guid. (Or even,
   to look up the type of the asset just by guid.)
   
   In the editor, we'd also like to be able to associate an asset with a path (in
   both directions), and add / remove / import / inspect &c various files.

   And it would be nice to be able to use the same kind of API for accessing assets
   in game, as in the editor. But, of course, it would also be nice not having to keep
   editor functionality in the core engine.

OK, so what would an runtime API look like?
   Something like:
   	
	future<T*> LoadAssetAsync(guid, type)
	T* LoadAsset(guid, type);
	void ReleaseAsset(guid);

   ...so this would require: map<guid, T*>
   or indeed: map<guid, RefCountedWrapper>

   How would this be initialized? Like, how to actually save the files? Let's read
   up on this in _teh ultimate source_. I suppose that technically we could leave
   everything in a separate file as well, to start with.

   Mmmm. Yes.

   First approach:
   	- AssetDatabase:
		- a wrapper around 2 maps: guidToPath, and pathToGuid.
		- expose as an engine-core service, not as read only, so a
		  shipped game can resolve assets w/o the editor present.


	- AssetRef<T>: stores a GUID and resolves lazily:
		- ask the AssetDatabase (or asset loader) for a given resource,
		  and cache it until invalidated.

Then, assetDatabase:
- oh, jolly good, I have a shared_ptr<void>, so I can save that in my map of loaded

  	unordered_map<GUID, shared_ptr<void>>

- if someone asks for an std::string:
shared_ptr<std::string> AssetDatabase::LoadAsset<std::string>(GUID)
{
	= ok, is this already loaded?
	= if it is, jolly good, return it
	= if not, look for the AssetLoader and load it,
		but store it as a shared_ptr<void>

	= then use std::static_pointer_cast<std::string>(stored_shared_ptr_to_void)
	  to return the actual thing.
}

std::static_pointer_cast<T>(std::shared_ptr<U>): creates a new shared pointer, pointing
  to a T, from an existing shared pointer, pointing to a U, by calling static_cast on the
  stored pointer. The new shared pointer will share ownership with the existing one!,
  so this is exactly what we need (see assetDbExperiments).


Regarding the AssetRef class.
- "Resolve" doesn't make sense to me. Why would I want to "resolve" that reference?
  I want to load or unload the thing that is at the end of it.

- So how about this:

	using LoaderFunction = std::shared_ptr<void>(*)(const std::string&);
	or
	using LoaderFunction = std::shared_ptr<void>(*)(const std::string_view);

	- AssetDatabase has:
	  std::unordered_map<GUID, std::shared_ptr<void>> _loadedAssets;
	  std::unordered_map<TypeID, LoaderFunction> _loaderFunctions;

	  template <typename T>
	  std::shared_ptr<void> DoLoadAsset(const std::string& path);

	  template <typename T>
	  void RegisterLoadFunction(LoaderFunction fn)
	  {
	  	_loaderFunctions.emplace(std::make_pair(GetTypeID<T>(), fn));
	  }

	  template <typename T>
	  std::shared_ptr<void> DoLoadAsset(const string& path)
	  {
	  	auto ldFn = _loaderFunctions.find(GetTypeID<T>());
		if (ldFn != _loaderFunctions.end())
		{
			return (*ldFn).second(path);
		}

		// handle error
	  }
